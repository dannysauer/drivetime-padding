# Architecture

## Overview

Drivetime Padding is a Google Workspace Add-on implemented with Google Apps Script. It watches a user's primary Google Calendar and creates travel-time events around eligible calendar events. The initial provider calculates driving time to and from an event location, plus a configurable buffer.

The add-on is intended for both consumer Google accounts and Google Workspace accounts and will be distributed through the Google Workspace Marketplace.

## Components

1. **Google Workspace Add-on**
   - Apps Script runtime
   - CardService settings and event-context UI
   - Installable Calendar change trigger
   - Daily repair/reconciliation trigger
   - Advanced Calendar service for event types, recurring instances, and private extended properties

2. **Synchronization engine**
   - Reconciles a rolling planning window, defaulting to 60 days
   - Processes the primary calendar only in v1
   - Treats recurring event instances as independent source events
   - Creates non-recurring generated events for each eligible instance
   - Updates or deletes generated events when the source changes or disappears

3. **Routing broker**
   - Small authenticated Cloud Run service
   - Receives origin and destination values
   - Calls Google Maps Routes API using server-side credentials
   - Returns only route duration and optional distance
   - Centralizes billing, quotas, abuse controls, and logging

4. **State and metadata**
   - User settings are stored in Apps Script User Properties
   - Generated events are linked to source events using Calendar private extended properties
   - A deterministic fingerprint avoids unnecessary Calendar writes

## Padding-provider model

Travel padding is the first implementation of a more general padding-provider interface. The MVP remains intentionally narrow: driving routes, two generated events, and OOO or optionally pattern-matched source events.

The internal design should nevertheless separate:

- source-event eligibility
- origin and destination resolution
- padding calculation
- generated-event planning
- event reconciliation

A provider accepts a normalized source event and user settings and returns zero or more desired generated-event specifications. The synchronization engine owns upsert, deletion, metadata, idempotency, and error handling.

Conceptually:

```text
Calendar event
    |
    v
Eligibility and normalization
    |
    v
Padding provider
    |
    v
Desired generated events
    |
    v
Generic reconciliation engine
```

The initial `drivetime` provider returns:

- an outbound event ending at the source start
- a return event beginning at the source end

Possible future providers include preparation time, post-meeting decompression, airport buffers, or arbitrary rule-based padding. These are explicitly out of scope for the MVP.

## Event eligibility

By default, a source event is eligible when all of the following are true:

- it is on the primary calendar
- it is inside the configured planning window
- it is a timed event, not an all-day event
- it has a non-empty Calendar `location` field
- it is a real `outOfOffice` event
- it is not generated by Drivetime Padding
- it is not disabled by a per-event directive

Users may optionally configure a subject pattern to include ordinary events. Pattern-matched events remain ordinary events; they are not converted to OOO events.

## Origin selection

Users configure a required default origin and optional home and office origins. Each origin may be a plain address or Google Place ID.

Origin selection order:

1. per-event origin override
2. matching Google Calendar working-location event, when enabled
3. configured default origin

The return route always ends at the same selected origin used for the outbound route.

## Recurring events

The system does not mirror recurring series. It expands recurring events into instances inside the rolling window and creates linked one-off padding events for each instance. This avoids maintaining a second recurrence graph and naturally supports edited, moved, and cancelled instances.

## Trigger and reconciliation model

Calendar update triggers indicate that the calendar changed but do not identify a specific changed event. Trigger executions therefore run a bounded reconciliation rather than attempting a single-event mutation.

A daily scheduled reconciliation provides eventual consistency and advances the far edge of the rolling window.

## Generated event metadata

Generated events use private extended properties similar to:

```json
{
  "dtpGenerated": "1",
  "dtpSchema": "1",
  "dtpProvider": "drivetime",
  "dtpParentEventId": "source-instance-id",
  "dtpParentICalUID": "source-ical-uid",
  "dtpParentOriginalStart": "2026-07-24T14:00:00-05:00",
  "dtpRole": "outbound",
  "dtpFingerprint": "sha256-value"
}
```

Human-readable subjects also use a predictable prefix:

```text
[Drivetime Padding] Travel to Doctor appointment
[Drivetime Padding] Return from Doctor appointment
```

## Security and privacy

- Calendar data remains in the user's Google account except for origin and destination values sent to the routing broker.
- The Maps credential is never embedded in Apps Script.
- The broker stores no route request data by default beyond operational logs required for abuse and reliability monitoring.
- OAuth scopes should be explicitly declared and minimized while still permitting background reconciliation and event writes.
